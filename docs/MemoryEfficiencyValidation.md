# Swift 接続・メモリ効率の修正と検証

これは前段階の検証記録。2.0 の現在の成果物と実測結果は
[Release2.0Validation.md](Release2.0Validation.md) を参照。

検証日: 2026-11-03（日本時間）

対象: `codex/tags-localization`。1.3.3 を基点とする開発中のコード。公開リリース、commit、push は行っていない。

2026-11-02 のレビューで指摘した 7 項目を修正した。Swift/C の公開 API は維持している。新しいライブラリは追加していない。

## 修正内容

| 指摘 | 対応 |
|---|---|
| R1: MemoryOnly・永続化無効時にも失効したデータが残る | 保存待ちへ移すときにも全体設定とルートの永続化方針を適用。保存対象のみ保持する |
| R2: Swift が同じ文字列を何度も作る | 一つの C 結果を変換する間だけ、同じポインター・長さの文字列を所有 Swift String として共有する |
| R3: タグ・診断情報の配列を重複生成 | 同じ C 結果内の同じ範囲から作る配列を共有する |
| R4: C API の文字列バッファを過大に予約する | 重複排除用の所有文字列をそのまま結果の保存領域へ移す。追加のバッファ予約と本文コピーを廃止 |
| R5: Description 全体の二重解析 | 新形式の判定は先頭ラベルだけを確認し、全言語の本文解析を 1 回にする |
| R6: キャッシュ復元後にメタデータ共有が切れる | 内容とファイル状態が同じものを、候補レコードの Arc へ再接続する |
| R7: キャッシュの JSON 往復と多重保存 | 型付きデータでマージし、JSON 化を入出力境界へ限定。候補から再構築できるカタログ一覧の重複保存を省く |

Swift の変換用索引は結果ごとに破棄する。返却した文字列・配列は Swift が所有するため、C 結果を解放した後も利用できる。言語を変更した後の結果と、以前の結果を同じポインター索引で結び付けない。

C の文字列は `Box<str>` が所有し、構築時の索引から返却結果の所有配列へ移す。文字列のアドレスは変わらず、返却結果を解放すると一緒に解放される。文字列容量を見積もるための重複した走査も削除した。

キャッシュの再共有は、ルート・表示パス・実体パス・サイズ・更新日時・ファイル同一性・メタデータ内容が一致する場合に限る。同じ Script-ID だけを理由に別ファイルを共有しない。異なる内容や古いファイル状態は上書きしない。

キャッシュ形式の版を **4** に更新した。言語選択規則の版は **3** のまま。旧形式 3 のカタログ一覧を含むキャッシュも読み込める。通常の ScanResult の返却形式は変えていない。独立して利用できるファイル一覧キャッシュは引き続きメタデータを保持する。

## 1,000 件での再計測

修正前レビューと同じ合成 JSX を使用した。3 言語の Description を各 4,096 バイト、共通タグ 20 種類、優先言語 `ja/en/fr` とし、Apple Silicon の Release ビルドで計測した。

| 確認項目 | 修正前 | 修正後 |
|---|---:|---:|
| MemoryOnly の TTL 失効後 | メタデータが残る | 解放される |
| MemoryOnly のノード上限退避後 | メタデータが残る | 解放される |
| 永続化無効時の失効後 | メタデータが残る | 解放される |
| Swift の Description 保存領域 | 4,000 個 | **1,000 個** |
| Swift の説明本文バイト数の合計 | 16,384,000 B（15.63 MiB） | **4,096,000 B（3.91 MiB）** |
| Swift のタグ配列の保存領域 | 4,000 個 | **1,000 個** |
| Swift の共通タグの文字列保存領域 | 20,000 個 | **20 個** |
| C の文字列本文の予約・確保量 | 14,165,407 B（使用は 4,283,906 B） | **4,283,906 B** |
| 初回スキャンの Description 全体解析 | 2,000 回 | **1,000 回** |
| Rust のキャッシュ復元後のメタデータ実体 | 2,000 個 | **1,000 個** |
| キャッシュ書き出し時の Rust 確保要求量ピーク | 85,358,341 B（81.40 MiB） | **34,926,120 B（33.31 MiB）** |
| キャッシュ復元時の Rust 確保要求量ピーク | 77,615,191 B（74.02 MiB） | **27,740,314 B（26.46 MiB）** |
| 保存キャッシュのサイズ | 24,693,855 B | **13,227,826 B** |

Swift のキャッシュ取得結果でも、説明文・タグ配列は同じ共有数だった。返却値の一部を変更しても他の値は変更されず、エンジン終了後も返却済みの文字列は有効だった。

上のバイト数は、文字列本文の保存領域と Rust の未解放の確保要求量であり、**プロセスの RSS や Scripta! 本体の使用メモリではない**。C の所有文字列を管理する配列等の管理領域は、文字列本文の行には含めていない。

## 回帰・互換性確認

- Rust/C API の全機能構成: **333 テスト成功**。
- Swift SDK: **70 テスト成功、失敗・スキップなし**。
- MemoryOnly、永続化無効、永続化するルートとの混在を、TTL とノード上限の両経路で確認。
- 保存対象のデータは保存完了まで保持し、保存完了通知後には解放する。
- 全体キャッシュと、カタログ・ファイル一覧を別々の順で読み込む場合の共有を確認。
- 旧形式 3、同じ Script-ID の別ファイル、内容・ファイル状態が一致しないケースを確認。
- C 文字列の重複排除と、構築用索引を解放した後のアドレス・内容の有効性を確認。
- Swift の文字列・タグ・診断配列の共有、値コピーを変更したときの独立性、言語変更後の独立性を確認。
- ユーザーが変更した 01・02 を含む JSX 10 件は、8 条件の読み取り結果が修正前と一致。
- 指定された旧スクリプト群のメタデータ **401 件**と、全文解析 **437 件**の結果が修正前と一致。
- 作り直した dylib を使う C クライアントでも、10 件・401 件の返却内容が Rust と一致。
- 既存の C 公開シンボルを維持。公開ヘッダーと Swift 公開 API の変更はない。
- Clippy は標準構成と全機能構成で警告をエラーとして確認。Rust の書式・Git 差分チェックも実施。
